## The one rule

## THE ONLY WAY TO QUERY PRODUCTION DATA

**Every question about production data — `SSASPROD`, `EDWPROD`, `ODSPROD` — is answered from this
machine by borrowing the gateway binding of a published semantic model. Do not carry probe PBIPs
to the jumpbox. Do not write script runners. Do not ask Zack to paste and run a probe.**

Host models to borrow, both in the `Zack (Validation)` workspace (PPU), both Zack-owned:

| Source | Host model | Connector in its partitions |
|---|---|---|
| `SSASPROD` / `BIQLTabular` | `19 - Safety Stock and Order Size (SSAS Import)` | `AnalysisServices.Database` — arbitrary **DAX** |
| `EDWPROD` / `EDW` **and** `ODSPROD` / `ODS` | `19 - Safety Stock and Order Size` | `Sql.Database` + `Value.NativeQuery` — arbitrary **T-SQL** |

The cycle, every time:

1. `connection_operations ConnectFabric` — workspace `Zack (Validation)`, the host model above.
   This reaches the XMLA endpoint `powerbi://api.powerbi.com/v1.0/myorg/Zack%20%28Validation%29`.
2. `table_operations Create` — a **new** table whose `mExpression` carries the probe query.
3. `table_operations RefreshWithXMLA` — **that table only**.
4. Read it with `dax_query_operations Execute` over the same connection.
5. `table_operations Delete` the probe table, then `List` to confirm the model is back to shape.

Rules that make this safe, all of them mandatory:

- **ADD a table. NEVER edit an existing partition.** A validated deliverable's query is never put
  at risk, and refreshing one table leaves every other table untouched.
- **Declare columns explicitly.** Schema is not inferred from a partition expression; creation
  fails without them.
- **Delete the probe when done.** A probe table left behind is drift.
- Probes execute against **production, through the production gateway** — keep them small.
- **Never host a probe in a model that is mid-validation.**
- An XMLA write is a sandbox act. Anything meant to persist goes into the repo PBIP and ships
  through `fab` publish, which overwrites the service copy.

Why borrowing is required: a newly created model needs its own gateway datasource binding, and
this account gets an empty array from the `gateways` REST endpoint. Only models that are already
bound can reach production.

What this does **not** cover, and still belongs to the jumpbox: gateway health, Report Builder and
Power BI Desktop GUI work, and querying a live-connect SSAS model — `executeQueries` and XMLA both
refuse those with `DatasetExecuteQueries_DatasetNotAllowed`.

Use `edw_schema\ssasprod.bim` for `BIQLTabular` metadata, `edw_schema\ssasprod_ish.bim` for ISH metadata, and `Cognos Reports\Extra\v2.xmla` only when intentionally investigating v2. `BIQLTabular` reads the `BIQL.*_v2` views for Sales and FactForecast and carries the v2 feature set (wired FactForecast, EUR measures, Forecast perspective) — check the current `ssasprod.bim` before assuming a field only exists in v2. - Source ladder for new reports (Nick Bubash): **SSAS Live → SSAS Import → EDW Import → ODS Import**. A fallback applies at the report or field level only after the higher source is evaluated and the dependency is documented. Do not retain an EDW/ODS dependency solely to cosmetically reproduce a legacy label when the production SSAS field is adequate. Perspectives only constrain perspective connections; a full-model connection sees base-table columns.
- Preferred SSAS Import shape: use a native DAX query against `SSASPROD` / `BIQLTabular`; define one filtered fact-table variable with `FILTER`; project the required line-grain columns with `SELECTCOLUMNS`; retrieve related attributes with `RELATED`; import raw additive quantity/value columns; and define simple local model measures over those imported columns. Apply stable row-eligibility predicates in the native query so SSAS filters before transfer, while leaving interactive/report filters in the Power BI model. Do not add query-scoped measures or `SUMMARIZECOLUMNS` unless the required output grain actually needs aggregation. Verify every `RELATED` path against `edw_schema\ssasprod.bim` and use model surrogate-key relationships rather than guessed natural keys. `Cognos Reports\19 - 1 - Inventory - Safety Stock and Order Size\19 - Safety Stock and Order Size (SSAS Import)\Safety Stock and Order Size.SemanticModel\definition\tables\Shipments.tmdl` is the validated reference implementation.
- Local SQL Server: `localhost`, Trusted_Connection, databases `EDW` and `ODS` mirror the snapshot under real schema/table names — shipped `.m` runs verbatim with the server swapped to localhost.
- Cloudflare (writeback): token in `writeback/CF Token.txt` (utf-8-sig). The ambient `CLOUDFLARE_API_TOKEN` env var is the wrong account.
